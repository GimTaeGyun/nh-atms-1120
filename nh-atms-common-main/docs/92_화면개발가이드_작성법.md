# 92. 화면 개발 가이드 작성법 — 새 화면마다 같은 형식으로

> 새 화면을 개발할 때마다(공통 구조 변경도 같은 형식, 예: 제3부 메뉴 DB 전환) [`09_권한관리_폐쇄망_적용가이드.md`](09_권한관리_폐쇄망_적용가이드.md)(화면 개발 가이드) 끝에 **제N부**를 이어 붙입니다.
> - 형식의 견본은 **제1부 권한관리**입니다. 2026-11-12 사용자 결정으로 이 형식을 표준으로 정했습니다.
> - 목적: 폐쇄망에서 **이 문서만 보고** 화면을 처음부터 옮겨 적을 수 있게 하는 것입니다. 순서대로 따라 하면 빨간줄(컴파일 오류)이 생기지 않아야 합니다.

## 1. 만드는 파일 (화면 하나당 2개 + 생성)

| 파일 | 누가 | 내용 |
|---|---|---|
| `tools/screen-guides/<화면키>.md` | 사람·Claude 가 씀 | 본문: §0 ~ §6 (아래 2장 틀). **부록은 쓰지 않음** |
| `tools/screen-guides/<화면키>.json` | 사람·Claude 가 씀 | 명세: `order`(제N부 번호), `screenKey`, `title`, `body`, `base`(diff 기준 커밋), `groups`, `steps`(§2 순서표와 같은 순서) |
| `docs/09_권한관리_폐쇄망_적용가이드.md` | **도구가 만듦** | `python3 -I tools/gen_screen_guide.py` — 머리(`_header.md`) + 화면 목록 표 + 부마다 본문 + 부록 A(새 파일 전체 · 기존 파일 diff) + 부록 B(SHA-512) |

- 소스를 고치면 **도구를 다시 돌려** 부록 A·B 를 새로 만듭니다(본문은 손으로 고침).
- `--check` 로 문서가 최신인지 봅니다(커밋 전).

```bash
python3 -I tools/gen_screen_guide.py
```

```bash
python3 -I tools/gen_screen_guide.py --check
```

## 3. 쓰는 규칙

1. **순서(§2·json steps)는 의존 순서** — 불리는 파일을 먼저, 부르는 파일을 나중에 둡니다. 저장할 때마다 빨간줄이 0 이어야 합니다.
   - 백엔드 순서
     1. 응답코드 TSV
     2. DTO — 서로 부르는 DTO 는 불리는 쪽 먼저
     3. 공통(`web/common`) 변경 — Mapper.java → XML → 그것을 부르는 클래스
     4. 업무 Rules → Mapper.java → Mapper.xml → Service → Controller
     5. ✅ `compileJava`
     6. 테스트(공통 테스트 diff → 업무 테스트 새 파일)
     7. ✅ `build`
   - 프론트 순서
     1. 공통 부품 변경(`components/*` diff)
     2. `screenIds.ts`(화면키 타입)
     3. `domain` → `api/endpoints` → `*Columns` → 팝업(`screens/popup`) → `*Parts` → `*Page`
     4. `registry.ts` → 홈 카드(메뉴 행은 코드가 아니라 메뉴관리 화면·DB — 2026-11-12)
     5. ✅ `npm run check`
   - 단계마다 "왜 이 순서"를 한 줄 적습니다. 예: "`AuthUserKey` 를 씀 → B2 다음".
2. **새 파일 = 전체 소스, 기존 파일 = diff.**
   - diff 는 **그 화면 관련 줄만** 보이게 합니다. 같은 파일의 다른 변경(다른 화면·삭제 작업 등)은 폐쇄망에 이미 반영됐다고 봅니다.
   - json step 에 `drop`(지금 파일에서 그 화면 줄을 고르는 정규식) 또는 `base`(그 화면 작업 직전 커밋)를 줍니다.
   - 둘 다 안 맞으면 `drop` 정규식을 좁게 씁니다(예: `sample\.authMgt`).
   - **파일/모듈 단위 반입(2026-11-13)**: 공통 변경처럼 파일을 통째로 덮어쓰게 할 때는 step 을 `"kind": "replace"`(부록 A 에 '전체 교체' + 파일 전체)로 씁니다(예: 제4부 UI 가독성 개선).
   - **뒤 부가 그 파일을 지웠거나 구조를 크게 바꿨을 때**: 앞 부의 step 에 `at`(그 부를 마친 커밋)을 넣어 그 시점 내용으로 고정합니다(예: 제3부가 `menuSeed.ts` 를 지워 제1·2부 F10 에 넣음). 파일을 지우는 step 은 `"kind": "delete"`.
   - **뒤 부가 같은 파일을 고쳤을 때**: 앞 부의 그 step 에 `undo`(`[[정규식, 바꿀 글], …]`)를 넣어 지금 파일에서 뒤 화면의 줄을 빼고 diff 합니다(예: 제2부 메뉴관리를 만들며 제1부의 `screenIds.ts`·`HomePage.tsx`·`api-messages.tsv` step 에 넣음). 부록 B SHA-512 는 언제나 지금 파일(모든 부 적용 뒤) 기준.
3. **프론트는 자세히.** §4 의 탭·팝업마다 아래를 적습니다.
   - 화면 구성(위→아래 번호)
   - 핵심 코드 조각 + 뜻
   - 쓰는 API
   - 쓴 공통 모듈
   - "왜 이렇게 했나"
4. **공통 모듈(§3)** 은 실제로 import 한 것만, 파일 경로·쓰는 법 한 줄과 함께 적습니다. 새로 만든 공통 부품(예: `rowButtons`)은 §2 에 diff 로도 넣습니다.
5. **DB·SQL**
   - 테이블·컬럼 이름은 tobe 정본 그대로(`docs/04_DB_규칙.md`).
   - 새 SQL 에는 "폐쇄망 개발 DB 확인 필요"를 적습니다.
   - 서버 명령·SQL 은 한 블록에 한 문장입니다.
6. **json `desc`** = "이 파일:" 뒤에 붙는 한두 줄. 테스트는 `(테스트)`, 문서·확인 SQL 은 앞에 표시합니다.
7. 문서·주석에 화면번호(AS-IS 번호)는 쓰지 않습니다. "AS-IS '<화면 이름>'" 처럼 이름으로 씁니다.

## 4. 새 화면 요청이 오면 (Claude 체크리스트)

- [ ] 화면 구현이 끝나면 `tools/screen-guides/<화면키>.md`(본문 §0~§6)와 `<화면키>.json`(order = 다음 번호, base = 작업 직전 커밋, steps = 의존 순서)을 만든다
- [ ] `python3 -I tools/gen_screen_guide.py` → `docs/09_…` 에 제N부가 붙고 화면 목록 표가 늘었는지 본다
- [ ] 부록 A 의 diff 가 그 화면 줄만인지(다른 변경이 섞였으면 `drop` 정규식으로 좁힘), `(변경 없음)` 이 없는지
- [ ] 프론트 `npm run check`, 백엔드 `gradlew build`, `gen_screen_guide.py --check` 통과 후 커밋
- [ ] 답변에 "§2 순서대로 새 파일/diff 적용 → ✅ 확인" 을 짧게 안내
